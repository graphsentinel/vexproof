vexproof

Evidence chains for VEX statements. For every vulnerability a scanner reports in a Go binary, vexproof collects what each tool can actually show and derives one OpenVEX status. Missing or contradictory evidence never becomes not_affected.

Apache-2.0. A lab that reproduces the measurements and the decision rules, not a production scanner.

The problem

A scanner lists dozens of CVEs; the developer says "we never call that code". VEX statements are meant to settle this, and a Kubernetes KEP (KEP-6377) proposes signed not_affected statements for Kubernetes' Go dependencies. But a VEX statement is an assessment, not evidence, and each not_affected justification needs a different kind of proof.

Go makes this harder. A Go program is usually one statically linked file, so the scanner reports every advisory of every module in it, and runtime relevancy that works per file marks every module as "in use" once the binary starts. The question that matters is narrower: is the vulnerable function in the binary, can untrusted input reach it, and did it run?

How it works

One chain per (binary, advisory). Each layer answers one question:

In the shipped binary?

The function table (.gopclntab) of the official binary, which survives stripping, with a positive control from the same package.

Can input reach it?

govulncheck call paths and CodeQL data-flow paths from untrusted input to the vulnerable function. Static: a path that can exist, not an execution.

Did it run?

Coverage counters of a rebuild of the same source, and kernel uprobes on the official binary.

Both in one request?

The exercise gate: a marked client request arrives as the vulnerable function's argument, and the trigger separates the last vulnerable build from the first fixed one in every pre-registered run.

Decision rules

  • affected: executed, an input path to the vulnerable function, and (for automatic chains) a passed exercise gate cited by sha256 in a review file. Static layers alone never produce affected.
  • not_affected (automatic chains): the vulnerable functions are missing from the shipped binary's full listing, a positive control from the same package is present, and the names occur nowhere in the binary's bytes (Go keeps the names of inlined functions there).
  • under_investigation: everything else, with a sub-state that names the missing evidence. "Not observed" alone never becomes not_affected.

Results

Kubernetes is the public test case: its binaries are official and anyone can check them, and its maintainers' decisions on these CVEs are documented. Six official binaries: kube-apiserver and kubectl at v1.28.2 and v1.36.5, kubelet v1.36.5, metrics-server v0.9.0.

Traps found by cross-checking the layers

  • CodeQL skips vendor/ by default: 0 instead of 3 call sites, so its "no taint path" means nothing.
  • govulncheck shows one example path; for HTTP/2 rapid reset it ran through a debug socket, while uprobes showed the real listener.
  • A go1.20 coverage build with -coverpkg but without the main package writes no counters at all.
  • vexproof's own symbol mapper ignored build tags and counted Linux code as execution of two Windows-only advisories, until the shipped-binary layer contradicted it. Fixed and disclosed.

Run it

On an amd64 Ubuntu 24.04 or 26.04 machine with sudo (8 vCPUs, 16 GB RAM, 60 GB disk recommended). A throwaway VM keeps your workstation unchanged:

multipass launch 26.04 --name vexproof --cpus 8 --memory 16G --disk 60G
multipass shell vexproof
git clone https://github.com/graphsentinel/vexproof.git
cd vexproof
scripts/platform.sh install
scripts/platform.sh cluster-up
scripts/lab.sh all

lab.sh all downloads the six official binaries (sha256-checked), regenerates their symbol listings, runs the fast path five times and compares every result with the expected ones. It ends with Result: OK. The report is results/run-1/report/vex-report.html. Details, full path and clean-up.

Use it on your own Go service

The CI recipe builds your service with coverage, deploys your own manifest into a throwaway k3d cluster, runs your workload commands and writes one chain and an OpenVEX document per symbol-level finding:

Two repositories are involved: your vexproof clone (the recipe) and the source of the service you test. From the vexproof clone, with your service's source cloned and vendored:

cp ci/metrics-server.json ~/work/mysvc.json   # edit: Go image, main package, manifest, workload
# fill src, out, manifest and cache paths with jq (README, step 3)
python3 ci/vexproof.py ~/work/mysvc-run.json  # exit 1 if a status in fail_on (default: affected)

The README first walks through metrics-server v0.9.0 with real URLs; those commands run as written (about 5 minutes).

Step by step, with every field explained. It has been run on Kubernetes components and metrics-server; your service needs its own workload profile.

Limits

  • Go binaries only.
  • Execution evidence is only as broad as the workload. "Not observed" is not "unreachable", and "executed" is not "exploitable".
  • Exercise gates are written per advisory and were run on an authenticated request path in a lab configuration.
  • No new vulnerability: every CVE here is known and fixed.
